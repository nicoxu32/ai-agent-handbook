# MCP：统一的到底是接入协议，还是业务能力？

## 知识点标题

<!-- field:chapter/k17/title -->
MCP：统一的到底是接入协议，还是业务能力？
<!-- /field -->

## 先这样理解

<!-- field:chapter/k17/intro -->
**一句话核心：MCP 统一的是“AI 应用怎么发现和调用外部工具”的接入协议，不是业务能力本身——连上 MCP 不等于有权限，更不等于系统变聪明了。**

MCP（Model Context Protocol）给 AI 应用和外部工具、上下文来源提供通用交互协议，价值是减少不同应用接入同一能力时重复适配。**它没有规定模型怎么思考，也不替你实现企业业务逻辑。** 比如通过统一协议发现和调用文件查询能力，账号授权和权限检查仍要单独做。

三个角色要分清：Host 是承载用户交互、模型和策略的 AI 应用；Client 是 Host 内连接某个 Server 的组件；Server 暴露工具、资源或提示模板，背后再去调企业原有 API。一个 Host 可以连多个 Server，每条连接由对应的 Client 管理。

**Tools、Resources、Prompts 是三类能力。** Tools 是可调用动作，例如查工单；Resources 是可读取的上下文，例如资源内容或数据描述；Prompts 是可复用的交互模板。服务可以只提供其中部分能力，客户端也未必支持全部，不能因为两端都标 MCP 就认为完全兼容。

协议层用 JSON-RPC 这类消息约定。常见连接方式有本地进程的 stdio 和远程 Streamable HTTP；远程虽然支持流式，但不能把旧教程里某种 HTTP／SSE 流程当成所有版本的固定做法。服务发现、版本声明和可选能力，要按双方支持的规范核对。

**版本确实会改变接入方式。** 本次核对的官方架构文档已描述 2026-07-28 版本的无状态请求与 server/discover 发现机制；维护较早协议的 SDK 时，不能直接套用新版发现流程。实现时固定兼容版本，按对应规范迁移。背住某一版初始化步骤，不等于理解了 MCP。
<!-- /field -->

## 放到产品里怎么判断

<!-- field:chapter/k17/decision -->
把 MCP、模型工具调用和业务 API 放在不同层看：模型提出调用，Host 决定是否执行，通过 Client 调 Server，Server 再办业务。授权、对象权限、幂等和审计照样要设计。

| 实际条件 | 首选做法 | 什么情况再升级 |
| --- | --- | --- |
| 多个 AI 应用复用同一能力 | 包成 MCP Server 统一接入 | 单应用接一个稳定接口，直接集成更简单 |
| 工具能发现但调用失败 | 查凭据范围、对象权限、后端业务状态 | 不把连接失败归给模型问题 |
| 接入工具越多、模型越选错 | 按任务加载相关工具集、规范命名 | 建工具目录，记录版本、提供者、可用状态 |
| 协议版本不一致连不上 | 固定兼容版本，按对应规范迁移 | 不混用新旧发现流程 |
| Server 返回内容被当成新指令 | 返回数据按外部内容隔离 | 防提示注入，不借描述提升信任 |

采用 MCP 的理由应是多应用复用、生态接入和维护收益，而不是“接上就自动成为万能 Agent”。

**面试官在考什么：** 考你分得清“协议统一”和“业务可信”——MCP 省的是适配成本，权限、幂等、审计一件都没少；并且知道协议版本会演进，旧教程不能直接套。
<!-- /field -->

## 项目中的应用场景

<!-- field:chapter/k17/scenarios -->
**企业工具中心。** 把工单查询、文档读取等能力包成受控服务，多种 AI 客户端按协议使用。目录记录提供者、权限、Schema、版本和可用状态；撤销连接后，新调用不能继续用旧授权。验收看撤权后新会话零调用。

**开发工作台接入。** AI 应用通过受支持的 MCP 服务读项目文档和错误追踪信息，按任务选工具。Server 返回的数据仍是外部内容，不能借描述文字升级成 Host 的系统指令。验收看工具选择准确率。

**多客户端共享同一能力。** 统一 Server，避免每个客户端单独适配。验收看新应用接入耗时。

**外部资源读取。** Server 返回的资源内容与系统指令严格隔离。验收看注入攻击拦截数。
<!-- /field -->

## 应用中经常遇到的问题

<!-- field:chapter/k17/troubleshooting -->
- **两边都支持 MCP，却连接不上。** 分别核对协议版本、传输方式、认证和能力支持；不把连接失败统一当成模型问题。
- **工具列表能看到，调用却失败。** 发现能力不等于拥有业务权限；查凭据范围、对象权限、参数和后端业务状态。
- **接入越多，模型越容易选错。** 按任务加载相关工具，规范命名与描述，记录版本变更；协议标准化没消除上下文拥挤。
- **照旧教程初始化失败。** 协议版本演进；固定受支持的组合，按对应规范迁移。
- **Server 返回文字被当成新系统指令。** 资源内容与系统指令隔离，描述文字不提升信任级别。
- **撤了连接，旧授权还能用。** 撤销连接后新调用不能复用旧授权；核对调用日志确认。

## 面试题 17.1

<!-- field:question/17.1/title -->
MCP、API 和 Function Calling 怎么配合？
<!-- /field -->

## 17.1 口述答案

<!-- field:question/17.1/answer -->
“API 是业务服务提供能力的接口；Function Calling 是模型生成工具调用意图和参数的方式；MCP 是统一 AI 应用与外部工具、资源交互的协议。它们可以在一次任务里连续出现。

比如模型选择查询工单，Host 校验后通过 MCP Client 调 Server，Server 再调工单 API，结果逐层返回。MCP 减少各客户端单独适配的成本，但不替代工单系统的权限和业务校验。

所以我会先看有没有跨应用复用需求和成熟服务，再决定是否采用。单一应用接一个稳定接口，直接集成可能更简单，不能把协议当业务能力本身。”
<!-- /field -->

## 面试题 17.2

<!-- field:question/17.2/title -->
设计 MCP 工具中心，需要管理哪些内容？
<!-- /field -->

## 17.2 口述答案

<!-- field:question/17.2/answer -->
“我会同时管接入兼容性和业务可用性。接入侧记录协议版本、传输、能力声明和认证方式；工具侧记录用途、参数、权限、提供者、版本、调用表现和失败类型。

发布工具前要验证描述和实际行为一致，工具变更会影响哪些 Agent、旧调用能不能继续用。运行时由 Host 和后端执行权限边界，不能让 Server 的描述自己获得更高信任。

对用户说明连接后能读什么、做什么、怎么撤销。评价中心不只看工具数量，还看接入耗时、正确调用率和维护成本；目录再丰富，模型选不对也不算平台成熟。”
<!-- /field -->

## 面试题 17.3

<!-- field:question/17.3/title -->
接入 MCP 服务后，最容易忽略什么？
<!-- /field -->

## 17.3 口述答案

<!-- field:question/17.3/answer -->
“最容易把协议连通误认为业务已经可信。工具发现成功，不代表当前账号有权限；参数符合 Schema，不代表订单状态允许操作；服务端返回文字，也不能当作新的系统指令。

我会分别检查版本与传输兼容、凭据隔离、对象权限、结果语义和工具变更。协议版本还会演进，客户端要固定受支持的组合，不能直接照旧教程拼接新规范。

出问题时沿 Host、Client、Server、业务 API 分层定位；涉及写操作仍保留确认和幂等。MCP 帮我们统一接入方式，可靠执行取决于完整的业务契约。”
<!-- /field -->
