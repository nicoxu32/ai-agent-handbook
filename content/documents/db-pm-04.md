# Agent 类产品和传统功能型产品在体验设计上最大的不同是什么？你会怎么设计，让用户愿意信任并放手交给 Agent 去执行任务？

## 面试题

<!-- field:doubao/db-pm-04/title -->
Agent 类产品和传统功能型产品在体验设计上最大的不同是什么？你会怎么设计，让用户愿意信任并放手交给 Agent 去执行任务？
<!-- /field -->

## 回答框架

<!-- field:doubao/db-pm-04/framework -->
1. 定位差异：从"用户操作工具"变为"用户委托 Agent 执行"——控制权转移
2. 信任是核心：透明（能看到 Agent 在做什么、为什么这么做）+ 可控（随时可干预/可撤回）
3. 失败/不确定时的设计：确认节点、兜底降级、失败成本前置
4. 用进度可见 + 结果预期管理，逐步建立用户信任
<!-- /field -->

## 口述参考答案

<!-- field:doubao/db-pm-04/answer -->
"我觉得最大的不同，是**用户和产品的关系变了**。传统功能型产品是'用户操作工具'——每一步用户都自己动手、自己负责；而 Agent 产品是'用户委托一个智能体去做事'，控制权从我手里交出去了。这个转变带来一个核心问题：**用户凭什么信任你、愿意放手？** 所以我认为 Agent 体验设计的灵魂，不是功能有多强，而是**信任设计**。

我围绕三个关键词来展开：**透明、可控、可预期**。

**第一是透明。** 用户放手的前提，是他能看到 Agent 在做什么、为什么这么做。我会把 Agent 的执行过程做成'可见的进度'——比如它在读哪个资料、查了什么、下一步要做什么，像给用户开了一扇窗，让他觉得'我看得见它，不是黑箱'。全程黑盒的 Agent，用户是不敢用的。

**第二是可控。** 信任不是一次建立的，而是靠'随时能收回控制权'建立的。我会设计清楚干预节点：用户随时可以暂停、改指令、撤回某一步；尤其在高影响动作（比如付款、发邮件、改配置）前面，一定放**确认节点**，让用户过一道手。这既降低风险，也让用户觉得'权力还在我手里'，他才会慢慢放手。

**第三是可预期——做好失败兜底。** Agent 一定会出错，关键是把失败的成本前置。我会想清楚：它不确定时是继续硬做，还是停下来问用户；出错之后有没有降级方案，能不能回到上一个可控状态。我会宁可让它在没把握的时候'认怂'停下来，也不让它闷头把事情搞砸。

最后落到做法上，我不会一上来就让 Agent 全权接管。通常先给用户**偏'半自动'的体验**——Agent 做一版、用户确认一版，用进度可见 + 结果预期管理，让用户在一次次'我放心、它没跑偏'里积累信任，再逐步放开权限。

所以我的结论是：Agent 体验设计的本质是**把控制权的转移设计得足够安全、足够透明**。用户不是被功能说服，而是被'我看得见、我控得住、它兜得住'说服，才会真正愿意把事交给它。"
