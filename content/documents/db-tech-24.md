# 讲讲"多 Agent"（Multi-Agent）架构——为什么要用多个 Agent 而不是一个 Agent？它一般怎么分工协作？

## 面试题

<!-- field:doubao/db-tech-24/title -->
讲讲"多 Agent"（Multi-Agent）架构——为什么要用多个 Agent 而不是一个 Agent？它一般怎么分工协作？
<!-- /field -->

## 回答框架

<!-- field:doubao/db-tech-24/framework -->
1. 概念：把复杂任务拆给多个"各司其职"的 Agent 协作完成，而非一个 Agent 大包大揽
2. 为什么用多个：单个 Agent 长任务易"忘、偏、乱"；专业分工让每个环节更专更稳
3. 常见分工模式：编排者/主管 Agent 拆任务 + 多个专业 Agent（如检索、执行、质检）执行 + 汇总
4. 协作机制：Agent 间通过"消息/产物传递"，可串行流水线也可并行/讨论式
5. 权衡与注意：多 Agent 带来编排复杂度、成本、协调失败风险，不是越多越好
<!-- /field -->

## 口述参考答案

<!-- field:doubao/db-tech-24/answer -->
"我先讲多 Agent 是什么。**它核心是把一个复杂的大任务，拆给多个'各司其职'的 Agent 去协作完成，而不是让一个 Agent 大包大揽。** 比如做一个'撰写市场报告'的任务，可以分成几个 Agent：一个负责检索资料、一个负责分析、一个负责成文、一个负责质检。每个 Agent 干自己最专长的一段，然后协作出结果。

那为什么要用多个而不是一个？我讲两个核心原因。

**第一个原因，单个 Agent 处理长任务容易'翻车'。** 一个 Agent 从头到尾做一件很复杂、很长的事，越往后越容易出问题——**会忘**（长任务到后面忘了前面的关键信息）、**会偏**（任务复杂，容易走偏方向）、**会乱**（多目标挤在一起，容易顾此失彼）。而拆成多个 Agent，**每个只负责一段更小、更专的任务**，单一职责更清晰，出错率就低，整体更稳。

**第二个原因，专业分工能提升质量。** 不同环节其实需要不同的'技能'和'检查标准'。检索要有检索的专项能力，成文要注重表达，质检要专门找错。让一个 Agent 既检索又写又要自查，容易'自己写的东西自己看不出问题'。**拆开之后，每个环节有专人负责，还能引入'互相检查'——比如让质检 Agent 去审成文 Agent 的输出**，质量更有保障。

那它一般怎么协作？我讲两种常见模式。一种是**流水线式（串行）**：主管 Agent 把任务拆好，A 做完传给 B，B 传给 C，一条线流下去。另一种是**并行/讨论式**：几个 Agent 同时开工，或者几个 Agent 像开会一样讨论、互相质询，最后汇总出一个更完善的结论。具体用哪种，取决于任务能不能并行、协作的复杂度。

最后我必须讲一下它的**权衡和坑**。多 Agent 不是越多个越好——它带来几个实打实的代价：**编排复杂度高**（怎么拆任务、怎么协调、谁最终负责）；**成本成倍增加**（每个 Agent 都要调用，token 消耗大）；**协调可能失败**（Agent 之间传错信息、互相矛盾，可能整条链崩掉）。所以我的判断是：**只有当任务确实复杂到单个 Agent 处理不了、或者拆开能明显提升质量和稳定时，才值得用多 Agent；简单任务用单个就够了。** 不要为了'看起来高级'而硬上多 Agent。

所以我的理解是：多 Agent 架构是用**'专业分工 + 互相检查'来换复杂任务的质量和稳定**，靠主管拆解、多 Agent 协作、产物传递来运作；但它有编排复杂、成本高、协调易失败的代价，**该用才用、够用即可**。"
