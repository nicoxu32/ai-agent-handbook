# 第三方 API 与账号授权：代表用户办事，需要哪些前提？

## 知识点标题

<!-- field:chapter/k23/title -->
第三方 API 与账号授权：代表用户办事，需要哪些前提？
<!-- /field -->

## 先这样理解

<!-- field:chapter/k23/intro -->
**一句话核心：API 接入不是"字段能传"就行——认证管你是谁、授权管你能干啥、业务状态管你成没成，三层分开验收，HTTP 200 不等于业务成功。**

接一个接口，不能只看请求字段通不通，还要看身份、授权范围、业务前置条件、返回状态、限流和错误语义。智能体可以组织调用，却不能替业务系统决定真实库存、余额或订单结果。

**认证和授权是两回事。** 认证确认调用者是谁，授权确认允许做什么。OAuth 常用于委托授权：用户在服务方流程里授予应用访问范围，应用拿到访问令牌；要确认用户身份，通常还要 OIDC 这类机制。看到 OAuth 不等于"知道用户是谁"。而且授权是按能力项给的：用户授权读日历，不代表也授权删除日程。

**令牌的范围和生命周期要管。** Access Token 用于访问资源，Refresh Token 在服务支持时用来换新访问令牌，两者用途和保护要求不同。授权会到期、会被撤销，账号也可能绑错。凭据要服务端安全保存，模型只接触完成任务必需的业务数据，Token 不进模型上下文。

**读、创建、修改、删除对应不同权限。** 用户授权应用读日历，不等于可以删日程；授权应用具备发布能力，也不等于每篇草稿都能不经确认直接发布。账号授权和当前动作授权要衔接起来。

**异步接口只有"受理"，没有"完成"。** 很多异步 API 返回的是受理状态，实际结果靠查询或回调拿。回调还可能重复、迟到、乱序，要校验来源、去重、结合状态机处理。
<!-- /field -->

## 放到产品里怎么判断

<!-- field:chapter/k23/decision -->
按任务需要的最小能力申请权限，向用户说明连了哪个账号、能做哪些事、怎么撤销。失败按类型分流：认证失败、权限不足、限流、业务拒绝、暂时故障，处理方式完全不同。接口能力撑不起产品承诺时，改产品流程，不让模型靠反复重试假装集成完整。

| 实际条件 | 首选做法 | 什么情况再升级 |
| --- | --- | --- |
| 申请权限 | 按任务最小范围申请，展示连接账号与撤销入口 | 需要扩范围时重新走授权，不默认继承 |
| 接口返回 200 | 查业务码、异步任务 ID 和最终状态 | 没有最终查询能力，UI 不许承诺实时成功 |
| 回调重复或乱序 | 校验事件标识和状态版本，去重处理 | 状态冲突回权威系统核验，不按通知时序定态 |
| 接口失败 | 授权过期走刷新或重授权；限流遵守等待提示 | 权限不足、业务拒绝不重试，转人工或补信息 |
| 写操作超时 | 先查是否已生效，再决定要不要重试 | 无法核验就标"结果待确认"，交用户处理 |

**面试官在考什么：** 他想听你分清认证、授权、业务状态三层，懂 OAuth 的 scope 边界、200 不等于成功、回调要去重，以及写操作超时必须先查状态再重试——权限和幂等意识。
<!-- /field -->

## 项目中的应用场景

<!-- field:chapter/k23/scenarios -->
**日程助手。** 读取空闲时间和参与者时区，先展示拟创建的日程，按授权写入并返回事件 ID；时间改了重新检查冲突；用户撤权后停止后续访问。验收看创建成功率和冲突漏判率。

**售后协同。** 查询订单和退款申请，提交符合规则的动作，靠回调加主动查询确认状态；用户看到的是"已受理"或"已完成"等真实阶段，不是一律成功。验收看状态准确率和超时未确认率。

**邮件代写助手。** 只有只读授权时只起草不发送，发送动作需要用户在明确范围里确认；草稿留在用户邮箱，不经过模型存储正文。验收看误发率和用户确认率。

**财务查询助手。** 只读授权查余额和流水，敏感金额字段脱敏展示；任何转账、付款动作一律拒绝自动执行，走人工复核流程。验收看越权操作拦截率和数据脱敏率。
<!-- /field -->

## 应用中经常遇到的问题

<!-- field:chapter/k23/troubleshooting -->
- **昨天能用，今天全部失败。** 检查令牌到期、被撤销、Scope 变化和账号绑错，别把授权问题当临时网络异常无限重试。
- **接口返回 200，业务没变化。** 检查业务码、异步任务 ID 和最终状态；UI 不能只凭传输成功就更新为完成。
- **同一回调更新了两次。** 验证事件标识和状态版本，去重处理；乱序通知不能把完成态退回较早状态，状态流转要按业务规则。
- **有读权限却尝试写操作。** 每个动作执行前核对当前意图是否在授权范围内；读授权不等于写授权，草稿不等于可发布。
- **Token 或凭据混进模型上下文。** 凭据只在服务端受控存储，模型只拿完成任务必需的业务数据；日志里也要打码。
- **写操作超时盲目重试。** 先查业务记录确认是否已生效，结合幂等能力再决定重试；状态未知时明确提示待确认，不能让用户发第二次造成重复退款。
- **用户撤权后应用还在访问。** 撤权信号要同步到所有任务通道，进行中的任务挂起或停止，后续调用按未授权处理。

## 面试题 23.1

<!-- field:question/23.1/title -->
OAuth 授权和用户确认操作是什么关系？
<!-- /field -->

## 23.1 口述答案

<!-- field:question/23.1/answer -->
"OAuth 解决应用被授予哪些资源访问能力，当前任务确认解决这次具体要做什么。用户授权日历写权限，只说明应用具备写的能力，不代表可以任意创建或删除所有日程。

我会在连接账号时展示范围和撤销入口，执行任务时核对当前意图、对象和必要确认。凭据由受控服务管理，不把 Token 放进模型上下文。

验收既测授权拒绝、过期和撤销，也测有读权限却尝试写、账号绑错这些情况。权限能力和任务意图都满足，才进入实际执行。"
<!-- /field -->

## 面试题 23.2

<!-- field:question/23.2/title -->
第三方 API 接入评审，你重点检查什么？
<!-- /field -->

## 23.2 口述答案

<!-- field:question/23.2/answer -->
"先看接口是不是真正覆盖用户任务，再看权限、状态和失败处理。字段能传只是基础，还要知道成功是受理还是完成，是否支持查询、回调、幂等和批量部分失败。

比如退款接口，除了提交金额，还要知道可退余额、订单范围、最终到账状态和超时后怎么核验。授权方式、限流、服务可用性和版本兼容也会影响产品承诺。

我会用正常、拒绝、超时、重复和撤权场景做联调，形成可恢复流程。没有最终状态查询能力，就不能在界面上承诺实时确认成功。"
<!-- /field -->

## 面试题 23.3

<!-- field:question/23.3/title -->
接口失败时，什么时候重试，什么时候转交用户？
<!-- /field -->

## 23.3 口述答案

<!-- field:question/23.3/answer -->
"先按原因区分。授权过期要刷新或重新授权，权限不足和业务拒绝通常重试也没用；临时网络异常或可恢复的服务错误可以有限重试，限流要遵守等待提示。

写操作超时尤其要先核对是否已经生效，结合下游幂等能力决定重试。同一动作状态仍未知时，明确提示待确认，不能直接告诉用户失败再发一次。

需要补身份、选替代方案或承担业务决策时，就让用户介入，同时保留输入和进度。合理兜底是给出有依据的下一步，不是把所有错误都变成'请稍后再试'。"
<!-- /field -->
