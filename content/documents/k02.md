# Token 与上下文：模型这次能看多少，为什么越聊越慢？

## 知识点标题

<!-- field:chapter/k02/title -->
Token 与上下文：模型这次能看多少，为什么越聊越慢？
<!-- /field -->

## 先这样理解

<!-- field:chapter/k02/intro -->
**一句话核心：Token 是模型算字数的单位，上下文窗口是“这一次问答”能装多少的上限——它不是记忆，装得下也不等于用得好。**

Token 是模型处理文本的计量单位，**不等于一个汉字或一个单词**。同一段中文，不同分词器（tokenizer）可能拆成不同数量的 Token。所以做产品别按字符数给用户承诺“能读多长”，预算要用目标服务的计量口径，界面展示也按服务实际口径来。

**上下文窗口是本次处理的容量，不是永久记忆。** 系统指令、用户消息、历史对话、检索片段、工具描述与工具返回都会占输入空间；还要按服务规则给输出和可能的推理 Token 留预算。窗口标称再大，也要核对最大输出限制——不能把全部容量都当成可生成的报告长度。

主流模型的上下文窗口目前从 64K 到 1M+ Token 不等。中文按常见分词约 1～1.5 个 Token 对应一个汉字估算，128K 窗口大致相当于 8～12 万汉字；但不同服务口径差异很大，面试时说“以目标服务的计量为准”比死背一个数字更稳。

推理分两个阶段，慢在哪里要分开找：**Prefill 处理输入、建立上下文表示，输入越长越慢；Decode 逐个生成输出 Token，答案越长越慢。** 所以“第一句话等了很久”和“已经开始但写得慢”是两个问题，排查路径不同；实际速度还受模型、批处理、硬件和服务排队影响。

KV Cache 缓存 Attention 的中间结果，避免生成每个新 Token 都把同样历史重算一遍；服务端 Prompt Cache 还能复用不同请求的公共前缀。但它们都不是用户长期记忆，也不会让过期内容自动更新——别在架构图里把它们画成“记忆”。

**上下文工程，是决定这一次到底给模型看什么。** 常见做法：保留结构化任务状态、压缩旧对话、按需读文件、把超长工具返回分页或提炼。摘要有损——金额、时间、用户已确认的操作范围要单独保存，别只靠摘要。长窗口只是“装得下”，不保证模型用好每一个位置的信息，该检索还是要检索。
<!-- /field -->

## 放到产品里怎么判断

<!-- field:chapter/k02/decision -->
先拆“输入装了什么、输出要多少”，再决定压缩、检索还是换窗口。教学例子：系统与工具说明占 8K，历史对话 30K，资料 50K，计划输出 6K，合计已 94K——还要核对目标模型对推理与输出的预留规则，不能只盯着那 50K 资料。

| 实际条件 | 首选做法 | 什么情况再升级 |
| --- | --- | --- |
| 对话一长就丢关键约束 | 结构化保存目标、金额、已确认状态，压缩叙事性历史 | 摘要仍丢关键字段，改为关键字段全量保留 |
| 单轮要塞入海量资料 | 先检索缩小范围，再决定直接读全文还是分块 | 检索后仍漏关键条款，评估“长窗口＋检索”组合 |
| 工具返回超长 | 分页、提炼或只取必要字段 | 必须全量时，独立存储＋按需读取 |
| 首字慢 | 查排队、缩短输入、利用受支持的前缀缓存 | 输入必须全量，评估换模型或批处理 |
| 输出慢 | 明确答案详略、设输出上限、流式展示 | 答案长度不可压缩，接受成本换质量 |

**面试官在考什么：** 他想确认你分得清“窗口大小≠记忆”“输入慢≠输出慢”这两对概念，并且把上下文工程（压缩、检索、结构化状态）当成产品日常工作，而不是只会说“换个大窗口”。
<!-- /field -->

## 项目中的应用场景

<!-- field:chapter/k02/scenarios -->
**长任务研究助手。** 对话越来越长时，保存研究目标、已验证结论、证据链接和待办，再压缩闲聊；后续任务按需回读文件。用户改变研究地区时，旧地区结果标为失效，不能让摘要继续把它当当前条件。验收看关键结论复用率与信息过期率。

**企业多技能助手。** 不必每轮把几百个工具的完整描述都塞进去。先按任务选相关工具集，需要时再加载更多；评估上下文节省的同时，检查真正需要的工具是否仍能被发现。验收看上下文占用下降与工具发现成功率。

**长文档报告生成。** 十份材料加历史讨论超窗时，先列材料清单分层处理，超长部分按需检索相关章节；输出前核对关键数字与引用的来源版本。验收看遗漏章节数与数字引用准确率。

**客服多轮会话。** 客户在第三轮才说出关键条件，模型必须复用前面已确认的诉求。把“已确认的诉求、金额、承诺”写进结构化状态，而不是只靠对话原文。验收看跨轮关键信息复用率。
<!-- /field -->

## 应用中经常遇到的问题

<!-- field:chapter/k02/troubleshooting -->
- **界面显示历史，模型却忘了。** 检查实际请求是否包含历史、摘要是否遗漏、窗口是否截断。聊天 UI 保存记录，不代表服务每轮都读到。
- **压缩后任务跑偏。** 对比压缩前后关键字段，尤其否定、金额与确认状态；把这些字段移到结构化状态，摘要主要承载叙述背景。
- **缓存命中低。** 检查可复用前缀是否稳定、动态时间与用户字段是否放在前面，并核对服务规则。不能为了命中缓存混用租户资料或过期授权。
- **首字慢被当成“模型变笨”。** 首字慢先查服务排队与输入处理，输出慢查生成长度；分开压测定位，不要混在一起调。
- **长窗口塞满，答案仍漏细节。** 装得下≠用得好。无关资料会干扰判断，关键信息夹在长文中间也会被忽略；聚焦式检索通常优于全量塞入。
- **用户说“上次说的你忘了”。** 上下文每次请求重建，不是持久记忆。跨会话偏好要有专门的记忆机制，与本次上下文分开设计。
- **超长工具返回截断导致误判。** 返回超限被静默截断，模型可能基于残缺数据作答；分页或提炼，并标记数据完整性。

## 面试题 02.1

<!-- field:question/02.1/title -->
有长上下文模型，为什么还要检索与上下文管理？
<!-- /field -->

## 02.1 口述答案

<!-- field:question/02.1/answer -->
“长窗口解决的是能容纳多少信息，并没有同时解决成本、更新、权限和有效使用问题。少量指定文档做整体比较，可以直接长上下文；从海量资料回答一个问题，更适合检索相关证据；要完整总结一组文件，则先列清材料再分层处理。

我会根据任务所需覆盖范围选择，而不是一律切块或一律全塞。还会测关键条件放在长文不同位置时能否被正确使用。就算没有超限，无关资料也可能干扰判断。

因此长上下文和 RAG 可以互补：检索负责缩小范围，较长上下文帮助容纳完整条款或多个证据；最终看完整正确率与成本，不用窗口数字代替效果。”
<!-- /field -->

## 面试题 02.2

<!-- field:question/02.2/title -->
用户说回答越来越慢，你如何区分输入与输出问题？
<!-- /field -->

## 02.2 口述答案

<!-- field:question/02.2/answer -->
“我先把排队、首字时间和生成阶段分开，再看输入输出 Token 的变化。长历史或巨大的工具结果可能拖慢输入处理；输出越长，逐步生成通常也越久。首字慢还可能是服务排队，不能只看 Token 猜结论。

如果输入重复，尝试删无关内容、压缩历史或利用受支持的前缀缓存；如果答案过长，先明确需要的详略和输出上限。流式展示能改善等待感，却不一定减少总耗时。

优化后用相同任务核对关键约束和答案完整性，再比较时延分布。不能通过截掉必要证据换取更快、却更不可靠的回答。”
<!-- /field -->

## 面试题 02.3

<!-- field:question/02.3/title -->
对话压缩和长期记忆有什么区别？
<!-- /field -->

## 02.3 口述答案

<!-- field:question/02.3/answer -->
“对话压缩主要是降低当前任务的上下文占用；长期记忆是决定哪些信息值得跨会话保存和再次使用。压缩摘要可能只活在这个任务里，不能自动视为用户永久偏好。

例如用户说‘这次报告控制在两页’，可以进入当前摘要；不能据此长期认定所有报告都只能两页。我会把目标、当前条件、已执行动作等结构化保存，摘要补背景，长期偏好另有写入与修改规则。

验证压缩时看原任务约束是否保留；验证长期记忆时看跨会话是否正确取用、是否过期和可删除。两者可能使用相似技术，但产品生命周期不同。”
<!-- /field -->
