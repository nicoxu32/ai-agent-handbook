# 结构化输出：格式能读，不代表内容能直接执行

## 知识点标题

<!-- field:chapter/k04/title -->
结构化输出：格式能读，不代表内容能直接执行
<!-- /field -->

## 先这样理解

<!-- field:chapter/k04/intro -->
**一句话核心：结构化输出是给模型定的数据接口——格式合法只是第一道门，字段对得上业务事实，这个动作才能执行。**

人能从一段会议纪要里猜出谁负责什么，程序却需要明确字段。结构化输出就是和模型约定数据接口：任务标题、负责人 ID、截止日期、来源、待确认项，一个都不能含糊。JSON 是常见表示，JSON Schema 则描述字段类型、必填项和允许值。比如约定订单结果必须包含 orderId、status、amount——字段合规之后，还要再去核验订单的真实业务状态。

**这里有三道不同的门，一道都不能省。** 第一，JSON 语法合法，程序能解析；第二，符合 Schema，比如金额必须是数字、状态只能在枚举里；第三，符合事实和业务规则，比如负责人真实存在、日期不是模型编的。前两道通过，第三道仍然可能失败。

有些服务支持约束解码，在生成时直接限制候选 Token，让结果符合受支持的 Schema 子集。这通常比在提示词里写一句"返回 JSON"稳得多，但要核对服务对 Schema、拒答、截断和流式结果的处理。关键是：**格式约束不懂外部业务事实**，它不能证明库存足够，也不能证明用户已授权。

还要把工具调用和结构化结果分开：工具调用描述"模型希望应用执行什么动作"，结构化结果描述"这个任务产出了什么数据"。一个提取结果可以先让用户编辑，再成为工具入参。**不要因为拿到了合法 JSON，就把它直接当成执行指令写进数据库。**

最常见的误区有三个：把"返回了 JSON"当成"可以写库了"；缺字段时编一个默认值填上；流式输出到一半就触发下游动作。这三件事都会让"格式正确"掩盖"内容错误"。
<!-- /field -->

## 放到产品里怎么判断

<!-- field:chapter/k04/decision -->
设计字段时先想清楚"未知怎么表达"：允许空值、单独的待确认状态，通常比编默认值可靠。稳定业务对象优先用 ID 而不是姓名；Schema 变更要带版本和兼容策略；身份、租户这类可信字段由程序注入，不能让模型自由填。

| 实际条件 | 首选做法 | 什么情况再升级 |
| --- | --- | --- |
| 输出经常语法错误或半截 | 用受支持的结构化输出/约束解码＋Schema | 服务不支持约束解码时，退化为提示词＋程序校验＋有限次重试 |
| 字段对、业务错（同名两人、金额超余额） | 接业务校验：通讯录解析 ID、余额与权限查询 | 校验不过就转人工或补问，绝不在格式层放行 |
| 原文缺信息（没说截止日期） | 字段允许空值或待确认状态，不编默认值 | 关键动作缺必填项，停下来问用户 |
| Schema 需要变更 | 只加可选字段、做版本管理、老流程回归 | 要改字段语义前先评估兼容，不热替换老流程 |
| 身份、租户等可信字段 | 服务端注入，不让模型填 | — |

**面试官在考什么：** 他想确认你分得清"语法合法、Schema 合规、业务事实正确"这三层门，会把未知显式表达、把执行权留在程序侧——而不是拿到 JSON 就写库，或靠重试和默认值把错误掩盖掉。
<!-- /field -->

## 项目中的应用场景

<!-- field:chapter/k04/scenarios -->
**会议待办创建。** 模型输出事项、依据时间戳和候选负责人；系统用通讯录解析人员，用户确认后再调用任务接口。会议没说截止日期就留待确认，不能把会议日期自动当截止日期。验收看误建任务数和待确认字段暴露率。

**采购申请提取。** 从邮件和附件提取商品、数量、预算与币种，程序检查币种和金额关系后生成草稿。合规的数字如果对应错行仍是错误，要回到附件定位核验。验收看关键字段准确率和串行列占比。

**客服工单自动建单。** 模型输出工单类别、问题描述、紧急度，程序校验类别在字典内、客户 ID 真实存在；涉及大额退款的高风险单必须转人工。验收看字段完整率和误建单率。

**合同关键信息抽取。** 抽取甲乙方、金额、签署日期，程序对照工商库核验主体身份，先给法务看可编辑草稿再归档。验收看关键字段准确率和主体核验通过率。
<!-- /field -->

## 应用中经常遇到的问题

<!-- field:chapter/k04/troubleshooting -->
- **JSON 正确却创建了错误任务。** 对照字段依据与业务对象，检查同名人员映射和相对日期时区；解析成功率不能解释语义错误。
- **流式输出到一半就触发操作。** 等完整结果与校验通过再执行；中间 Token 只是未完成数据，截断后要明确失败或恢复。
- **缺字段就无限重试。** 区分格式错误与源信息缺失；前者可有限修复，后者补问或保留未知——重试次数补不出不存在的事实。
- **格式重试十几次仍失败。** 检查是不是输出预算被截断、Schema 里有没有模型难遵守的深层嵌套枚举；先调预算和简化 Schema，不要无限重试烧钱。
- **模型把"候选人名单"写成了"已确认负责人"。** 候选与确认要分成两个字段，确认动作必须来自用户；不能让措辞模糊把未确认状态变成已执行。
- **接口升级后老流程突然报错。** Schema 变更没做版本兼容；新增必填字段会打破旧请求，灰度发布并跑老流程回归。
- **金额"看着对"其实串行了。** 合规的数字对应错行仍是错；回原文按位置核验，不能按文本相似度放行。

## 面试题 04.1

<!-- field:question/04.1/title -->
JSON Mode、Schema 约束和业务校验有什么区别？
<!-- /field -->

## 04.1 口述答案

<!-- field:question/04.1/answer -->
"它们约束的是不同层次。JSON Mode 通常帮模型生成可解析的 JSON；Schema 约束进一步要求字段、类型和枚举符合约定；业务校验才判断这些字段是否真实、允许使用。具体保证要看服务定义，不能只根据功能名称猜。

比如负责人字段是合法字符串、也符合 Schema，但这个名字在公司里可能对应两个人；退款金额是合法数字，却可能超过可退余额。这些都要查业务系统和规则校验。

我会分别记录结构失败与业务失败，让未知值有明确表示。涉及执行时，格式校验只是前置条件之一——不是拿到 JSON 就开始写数据库。"
<!-- /field -->

## 面试题 04.2

<!-- field:question/04.2/title -->
把自然语言转成可执行任务，你会怎样设计字段？
<!-- /field -->

## 04.2 口述答案

<!-- field:question/04.2/answer -->
"我会先围绕业务动作定义最小字段，再定每个字段的来源和校验方式。比如创建任务要有标题、负责人 ID、截止时间、来源和待确认项；身份、租户由服务端提供，不交给模型猜。

负责人先提取候选姓名，再由通讯录解析；相对日期按会议时间和时区转换，原话没说就留空。写操作前展示可编辑草稿，把未确定项解决后再执行。

字段设计还要考虑后续变更：新增可选字段通常容易兼容，改字段语义可能让老流程误用，所以要版本和回归。我的标准是——每个会影响动作的字段都有依据，而不只是结构漂亮。"
<!-- /field -->

## 面试题 04.3

<!-- field:question/04.3/title -->
输出不合规时，是修复、重试还是让用户补充？
<!-- /field -->

## 04.3 口述答案

<!-- field:question/04.3/answer -->
"先判断失败性质。格式不完整可能是输出被截断，要调预算或重新生成；语法错误可以受控修复，但修复后要重新校验；如果缺的是原始信息，就该询问或保留未知，不能让模型多试几次猜一个值。

对已有的正确字段我会保留草稿，避免全部推翻。自动修复只允许改变表达结构，不得悄悄补上金额、负责人这些关键事实。写操作在结果完整且业务校验通过前不执行。

监控上把格式失败、源信息缺失和业务冲突分开统计，才能决定改 Schema、补交互还是改模型——靠填默认值掩盖错误，是最省事也最危险的做法。"
<!-- /field -->
