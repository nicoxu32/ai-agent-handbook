# Agent 执行循环：下一步由谁决定，什么时候该停？

## 知识点标题

<!-- field:chapter/k14/title -->
Agent 执行循环：下一步由谁决定，什么时候该停？
<!-- /field -->

## 先这样理解

<!-- field:chapter/k14/intro -->
**一句话核心：Agent 的本质是一个“观察—判断—行动”的反馈循环——模型决定下一步，系统负责执行并把真实结果交回来，直到满足停止条件；没有停止条件和预算控制的循环，只是一个会烧钱的聊天框。**

不同产品对 Agent 的命名不完全一致，这里只抓一种具体机制：模型根据目标、当前状态和环境反馈决定下一步动作，应用执行后把真实结果交回，再继续判断。核心是反馈循环，不是头像、聊天框或“自主”两个字。

典型一轮是：读取当前目标与状态 → 选工具和参数 → 系统校验并执行 → 接收结果 → 更新状态 → 继续或结束。**执行失败必须成为新的观察**，不能让模型忽略失败、自顾自写完成总结。

ReAct 强调判断、行动、观察交替进行；先规划后执行则先做任务分解，再依结果调整。前者灵活但可能绕路，后者便于追踪但早期计划假设错了就整体失效。真实系统两者混用：计划是一份可修订的执行依据，不是必须照做的剧本。

**任务越长，可靠性越要靠工程补。** 一个教学简化：十个必要步骤相互独立、每步成功率 95%，全部成功约为 0.95 的十次方，也就是 60%。真实错误不独立、还能重试恢复，但这个例子说明——单步准确率代表不了完整任务能力。

所以上线前必须定义清楚：允许用哪些工具、目标范围、最大轮次、时间、Token 或费用预算，以及什么状态算成功、什么情况算失败、什么情况转人工。框架可以组织循环，可信状态和副作用控制仍然是业务系统的事。
<!-- /field -->

## 放到产品里怎么判断

<!-- field:chapter/k14/decision -->
先找任务里真正不确定的步骤。能由固定条件决定的动作，Workflow 更合适；只在需要探索或动态分解的环节用 Agent。验收以任务最终结果为单位，同时看成功是不是依赖了额外人工、有没有超预算。

| 实际条件 | 首选做法 | 什么情况再升级 |
| --- | --- | --- |
| 步骤可由固定条件决定 | 确定性 Workflow | 只有探索环节局部嵌 Agent |
| 需按工具结果动态选下一步 | 受限 Agent：限定工具集＋预算 | 稳定后把该环节固化回流程 |
| 证据不足、查不到 | 换有效策略或补问用户 | 预算耗尽就返回缺口和可继续路径 |
| 同一动作反复执行、无进展 | 识别无进展并停止 | 保留已完成产物，说明从哪继续 |
| 写操作已“提交” | 以系统真实回执为准 | “已提交”不等于“已完成”，必须核验 |

展示动作、证据和结果即可，不需要把不可验证的长篇思考文本当成执行证明。

**面试官在考什么：** 考你“单步成功率≠任务成功率”的复利意识，以及你能不能用预算、停止条件和真实回执把循环管住，而不是只画一张架构图。
<!-- /field -->

## 项目中的应用场景

<!-- field:chapter/k14/scenarios -->
**研发问题定位助手。** 先读报错和相关文件，再跑受控测试，按失败现象继续定位；修改后验证目标问题和相关行为。完成标准是修改符合要求且检查通过，不是生成了多少补丁。验收看端到端任务成功率。

**客服处理助手。** 根据用户描述查订单、政策和物流，判断要补问、解释还是发起允许的售后操作；查到订单不等于退款完成，最后核验真实业务状态。验收看误退款率和转人工后解决率。

**资料探索任务。** 多轮检索直到证据齐全，或预算耗尽返回“还缺什么、从哪继续”。验收看预算内收敛率和超时返回缺口的比例。

**代码与数据操作任务。** 写操作执行前确认、执行后核验状态。验收看重复执行次数和错误状态传播导致的连带失败数。
<!-- /field -->

## 应用中经常遇到的问题

<!-- field:chapter/k14/troubleshooting -->
- **一直搜，就是不结束。** 查是不是缺完成标准、反复用同一查询、证据根本不够；设轮次预算，到顶返回缺口。
- **接口失败了，模型仍说成功。** 工具结果要结构化区分受理、完成、失败；最终答复从可信任务状态生成或核验。
- **计划很完整，执行却跑偏。** 每轮核对动作是否仍服务当前目标；目标变了就重规划，旧计划依赖失效后硬走只会错下去。
- **步骤一多，错误层层传播。** 一个参数错，后面的检索、报告、保存全建立在错误对象上；按链路记录定位失败节点。
- **重试把同一写操作发了多遍。** 幂等键加状态查询；超时先查是否已生效，再决定重发。
- **权限或参数被拒，还一遍遍试。** 区分权限拒绝、非法参数和临时网络错误；前两类不重试。
- **拿长篇思考当执行证明。** 思考不可核验；验收只看动作、证据和真实结果。

## 面试题 14.1

<!-- field:question/14.1/title -->
一个 Agent 的最小执行闭环包括什么？
<!-- /field -->

## 14.1 口述答案

<!-- field:question/14.1/answer -->
“至少要有目标、当前状态、可调用工具、执行反馈和停止判断。模型在这些信息下选动作，应用负责校验与执行，结果再进入下一轮状态。只有一次模型输出加几个接口名称，不等于闭环已经可靠。

以客服处理为例，查订单后可能需要补信息，也可能有资格申请退款；提交申请后还要核对系统到底是受理还是完成。每一步都必须基于真实返回继续判断。

我会先限制任务范围和预算，定义什么状态算成功、什么情况应停止或交给人。最重要的是让循环收敛到可核验结果，而不是无限尝试。”
<!-- /field -->

## 面试题 14.2

<!-- field:question/14.2/title -->
怎样控制 Agent 的死循环与无效工具调用？
<!-- /field -->

## 14.2 口述答案

<!-- field:question/14.2/answer -->
“我会同时控制动作范围和进展。只给当前任务需要的工具，明确参数和错误类型；记录已执行动作及结果，识别同样条件下重复搜索或重复失败。再设最大轮次、耗时和费用预算作为硬上限。

权限不足、参数明确非法、业务拒绝，不该按临时网络错误一遍遍重试。证据不够时可以换有效策略或补问，但新动作必须说清预期解决什么缺口。

停止后保留已完成产物和原因，让用户知道能从哪里继续。评测会加入空结果、持续超时和互相冲突的反馈，检查系统是否及时退出，而不仅测理想成功路径。”
<!-- /field -->

## 面试题 14.3

<!-- field:question/14.3/title -->
单步正确率很高，为什么完整任务成功率仍低？
<!-- /field -->

## 14.3 口述答案

<!-- field:question/14.3/answer -->
“因为任务需要多个步骤同时成立，前面的错误还会影响后面的判断。一个工具参数错了，后续检索、报告和保存可能全建立在错误对象上。单步平均值也会掩盖某个特别关键的薄弱环节。

我会按完整任务统计成功，再用链路记录找最常见的失败节点，区分可恢复失败、错误状态传播和终止判断错误。优先修对最终结果影响最大的环节，必要时把稳定部分改成确定性流程，减少不必要的模型决策。

重复运行同一类任务也很重要，第一次成功不代表稳定。我要看到端到端结果、人工介入和成本一起改善，才认为 Agent 能力真的提升了。”
<!-- /field -->
