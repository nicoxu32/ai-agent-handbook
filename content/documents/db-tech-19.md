# 讲讲"上下文缓存"（Context Caching）——它是什么？为什么能明显降本、提速？

## 面试题

<!-- field:doubao/db-tech-19/title -->
讲讲"上下文缓存"（Context Caching）——它是什么？为什么能明显降本、提速？
<!-- /field -->

## 回答框架

<!-- field:doubao/db-tech-19/framework -->
1. 概念：把重复出现的"输入前缀/固定上下文"缓存起来，命中时不用重复计算
2. 为什么有效：模型对相同输入的处理结果可以复用，尤其系统指令、固定文档重复出现
3. 降本原理：命中的部分不再按满额计费，只收缓存命中的低价甚至几乎免费
4. 提速原理：跳过重复的预填充（Prefill）阶段，首字响应更快
5. 适用场景与注意：固定系统提示/长文档/多轮对话；缓存可能失效、更新时要清缓存
<!-- /field -->

## 口述参考答案

<!-- field:doubao/db-tech-19/answer -->
"我先讲上下文缓存是什么。**它是在模型处理大量相同输入时，把重复出现的那部分输入（尤其是前缀）的中间处理结果先存起来，下次遇到同样的输入，直接复用，不用重新算一遍。** 你可以理解成：**把'每次都重复算'的开销，变成了'算一次、反复用'。**

为什么这个优化这么有效？因为在很多真实场景里，输入有很大一部分是**固定的、重复的**。比如一个企业客服系统，每次调用都要带上**一大段固定的系统指令**（告诉模型它是什么角色、要遵守什么规则）；再比如 RAG 场景，**一份长文档会被反复查询**，前面的文档内容每次都一样。这些'重复的前缀'，正是缓存能发挥价值的地方。

那它为什么能**降本**？我给你讲计费的逻辑。大模型是**按输入 token 计费**的，但针对缓存，通常有一套**更便宜的计费规则**——**命中了缓存的那部分 token，费用大幅降低，甚至接近免费**。所以当你的系统指令、固定文档占了输入的很大比例，缓存一开，能省下一大块输入成本。对高频、长上下文的场景，这个降本非常可观。

那它为什么能**提速**？这要从模型生成的两个阶段讲。模型处理请求分两步：**预填充（Prefill）**——先把整段输入算一遍、理解它；**解码（Decode）**——逐字生成回答。上下文缓存的价值在于：**如果输入的前缀命中了缓存，就可以跳过重复的预填充阶段**，直接从已有结果接着算。预填充往往是响应里最耗时的一部分，跳过它，**首字响应（TTFT，第一个字出来的时间）会明显变快**，用户感觉就是'回答来得更快了'。

最后我讲几个要注意的点。**一是缓存不是永远有效的**——它有有效期、也受 token 数限制，长输入缓存可能存不下；**二是上下文一旦更新，缓存会失效**——比如系统指令改了、文档更新了，旧缓存就不能再用，需要重新计算；所以做缓存时要清楚'什么时候能复用、什么时候该刷新'。**三是它是自动还是手动**——有的平台自动做前缀缓存，有的需要主动管理，要按平台机制来用。

所以我的理解是：上下文缓存是**利用'输入大量重复'这个特点，把重复的预填充结果存起来复用**，从而既大幅降低 token 成本、又加快首字响应。它对'固定系统指令 + 长文档 + 高频调用'的场景尤其有效，是 AI 服务降本提速里很实用、也常常被忽略的一招。"
